## 1. 異常検知の仕組み

### 何が困るのか

定期実行を始めると、**失敗しても誰も気づかない**状態になります。

現在もログには `ERROR` と出るのですが、監視用途には使えません。理由は2つあります。

**理由1: 1回の失敗で ERROR が8行出る**

原因と対処を並べて出しているためです（人が読む分には親切ですが、機械には不向きです）。
「異常が何回起きたか」を数えられません。

```
grep '2026-09-18' run.log | grep ERROR  → 8行ヒット（失敗は1回だけ）
```

**理由2: 「動いていない」ことを検知できない**

cron の設定ミスやサーバ停止でスクリプトが起動しなかった場合、
ログには何も出ません。**正常に動いて変更が無かった場合と区別がつきません。**

IPSet が許可リストの場合、これは「気づかないうちに古いIPのまま放置される」ことを意味します。

### ご提案

**ログに「1回の実行につき必ず1行」の結果行を追加します。**
既存の `ERROR` 行はそのまま残します（人が原因を追うのに必要なため）。

```
[waf-ipset.sh]    RESULT 2026-09-18 04:05:11 status=ok       code=0 ipset=google-list before=180 after=182
[waf-ipset.sh]    RESULT 2026-09-18 04:15:03 status=nochange code=3 ipset=bing-list   before=28  after=28
[waf-ipset.sh]    RESULT 2026-09-18 04:25:44 status=error    code=1 ipset=claude-list reason=aws_call_failed
[get-google-ip.sh] RESULT 2026-09-18 04:05:02 status=ok      code=0 count=182
```

役割を分けます。

| | 用途 | 行数 |
|---|---|---|
| `ERROR` 行 | 人が原因を追う | 1回の失敗につき複数行 |
| `RESULT` 行 | 機械が監視する | **1回の実行につき必ず1行** |

これにより、監視する側は次のように書けます。

```bash
# ① 前日の異常だけを拾う
grep RESULT /var/log/waf-ipset.log | grep "$(date -d yesterday +%F)" | grep 'status=error'

# ② そもそも実行されたかを確認する（4主体なら4行あるはず）
grep RESULT /var/log/waf-ipset.log | grep "$(date -d yesterday +%F)" | wc -l
```

②により「動いていない」ことも検知できるようになります。

`status=` の値は3つに限定します（増やすと監視側の条件が複雑になるため）。

| 値 | 意味 | 終了コード |
|---|---|---|
| `ok` | 実行して変更した | 0 |
| `nochange` | 実行したが変更なし（正常） | 3 |
| `error` | 失敗した | 1 または 2 |

### 通知を外付けする仕組み

あわせて、**異常時に任意のコマンドを呼び出す設定**を用意します。

```bash
# config.sh に追加する設定
# 異常時に実行するコマンド。空なら何もしない。
HANDLER_COMMAND="/opt/bin/handler.sh"
```

呼び出され方:

```
handler.sh exception <スクリプト名> <終了コード> <理由>
```

利用者側で用意していただくスクリプトの例（Slack通知の場合）:

```bash
#!/usr/bin/env bash
# handler.sh
case "$1" in
  exception)
    curl -s -X POST -H 'Content-type: application/json' \
      --data "{\"text\":\"WAF同期に失敗: $2 (code=$3, $4)\"}" "$SLACK_WEBHOOK_URL"
    ;;
esac
```

**スクリプト本体は Slack を知りません。** 通知先を変えても本体は変更不要です。
メール通知や監視システムへの連携に差し替えることもできます。

### 監視方式の選択

上記は2つの方式を含んでいます。**どちらか一方でも構いません。**

| 方式 | 長所 | 短所 |
|---|---|---|
| A. ログを grep する | スクリプト側の変更が小さい。既存の監視基盤に乗せやすい | 監視する側の仕組みが別途必要 |
| B. handler で通知 | 即座に通知が飛ぶ。監視基盤が無くても成立する | 通知スクリプトを別途用意する必要がある |
| A + B | 取りこぼしが無い | — |

既存の監視基盤（Zabbix / CloudWatch Logs など）がある場合は A だけで十分な可能性があります。
**現在の監視体制をお教えいただければ、どちらが適切かご提案できます。**

## 5. IPv6対応

取得側は対応済みですが、反映側が IPv4 専用のため、
Google が公開している約1,000件の IPv6 を反映できません。

対応するには IPv6 用の IPSet を別途作り、スクリプトを拡張する必要があります
（AWS の仕様上、1つの IPSet に IPv4 と IPv6 を混在させられないため）。

**そもそも IPv6 のクローラを制御する必要があるかどうか**から、ご確認いただきたい項目です。
自社サイトが IPv6 でアクセスを受けていない場合、対応は不要です。
